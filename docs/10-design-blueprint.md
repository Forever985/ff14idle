## 1. 先定调：这个游戏到底做什么

### 1.1 参照物：wow-idle 的成功要素（艾泽拉斯公会物语）

把它的核心闭环抽干，其实只有五步：

```
招募(members) → 编队/pick 职业与天赋 → 派遣远征(离线计时) → 收获战报+战利品 → 养成(等级/装备/天赋/技能)
                                                              ↑                    │
                                                              └──── 挑战更高副本 ◄──┘
```

外加四条"留存管线"：**竞技场 PvP（异步）、战场（异步）、任务/成就（目标）、生产制造（资源链）**。

它的工程量分配（来自 `08` 的模块清单）很说明问题：
- 内容数据表就占了 5,518 行（`content.js`）+ 926 行（`items.js`）——**内容量本身就是游戏**；
- 战斗模拟 4,594 行、主循环 3,641 行——**自动化引擎是技术核心**；
- 界面层 8,692 行——**放置游戏一半的体验在"看数字涨"的呈现**。

### 1.2 FF14 的差异化机会（重要）

直觉上"FF14 更复杂所以更难放置化"，但实际读下来结论**相反**：

FF14 里存在大量**天生就是放置玩法**的系统，WoW 反而没有：

| FF14 原生系统 | 它本来就是什么 | 放置化难度 |
| --- | --- | --- |
| **Duty Roulette（任务轮盘）** | 每日随机副本，固定收益 | ★ 几乎零改造 |
| **Wondrous Tails（天书奇谭）** | 周常"九宫格贴纸"兑奖 | ★ 现成的每周留存钩子 |
| **Retainer Ventures（雇员探险）** | 派雇员出去，若干小时后回来交货 | ★★ **就是放置收益本体** |
| **Free Company 潜艇/飞空艇** | 定时派遣、带回材料 | ★★ 同上 |
| **Island Sanctuary（岛屿庇护所）** | 离线生产、动物饲养、建造 | ★★ 现成的离线生产层 |
| **Cosmic Exploration（宇宙探索）** | 太空生产/机甲指令 | ★★ 现成的二期离线层 |
| **Deep Dungeon（深层迷宫）** | 无限层数、独立等级、赛季排行 | ★★ 现成的无尽塔 |
| **Occult Crescent / Eureka / Bozja** | 野外独立成长岛 + 独立货币 | ★★ 现成的"独立成长岛" |
| **FATE** | 地图上定时刷新的公共事件 | ★ 现成的挂机刷怪 |
| **Hunt（狩猎）** | 每日/每周讨伐目标 | ★ 现成的日常 |
| **幻境武器(Relic) 长链** | 多阶段、跨内容、超长材料需求 | ★★ 现成的长线至尊目标 |
| **7.56 Crucible of the Unbroken** | **棋盘 roguelike + 幻兽编队 + 计分赛季** | ★★ 现成的 roguelike 挂机层 |
| **8.0「每周自选进度」** | 任务/副本/FATE/前线都能涨进度 | ★★★ **官方自己把 MMO 周常做成了可自由安排的资源分配** |

> **结论**：FF14 的"放置化"不是硬塞，而是**把官方本来就有的离线/周期系统显式化**。
> 这是本项目最大的叙事优势——玩家会觉得"这很 FF14"，而不是"这是个套皮放置游戏"。

## 2. 三个必须先拍板的核心决策

### 决策一：玩家扮演谁？（决定整个养成结构）

| 方案 | 描述 | 优点 | 致命问题 |
| --- | --- | --- | --- |
| **A. 公会会长式**（照抄 wow-idle） | 你是部队长，招募大量无名冒险者 | 现成模板，收集感强 | **不像 FF14**——FF14 的故事里"你"就是唯一的英雄，招募路人毫无代入 |
| **B. 唯一光战式**（最正统） | 一个角色，靠"一角色全职业"撑内容 | 最 FF14，职业切换是官方核心卖点 | 只有 1 个单位，放置游戏最缺的"编队/收集"张力不足 |
| **C. 拂晓血盟式**（推荐 ⭐） | 你=光之战士（可切换全部战斗职业）；**队友=拂晓血盟成员**（对应官方 Duty Support / Trust 语义） | 既正统又能收集；官方已经给了"NPC 队友参战"的合法性 | 需要设计伙伴的独立成长轴 |
| **D. C+A 混合**（最稳） | 光战本人 + 拂晓成员 + 后期开放"部队招募"量产兵 | 前期叙事、后期刷量 | 系统复杂度上升，MVP 不做 |

**推荐 C，并把"招募量产冒险者"留到 v2 作为"部队/自由部队"扩展。**

> ### 📌 修订（2026-09-17，实现阶段）：C+D 的混合，而且是**用户拍板**的
>
> 实际做成了 **C+D 混合**（原方案里标为"MVP 不做"的那个）。理由是玩起来确实单调：
> 名角全是"章节到了自动送"，**没有"获得"这个动作，也就没有"得到"的感觉**。
>
> 最终形态（与需求方逐条确认过）：
>
> | 类别 | 获得方式 | 机制特权 |
> | --- | --- | --- |
> | **名角**（18 名剧情人物） | 主线章节 + 关键里程碑（塔层数 / 试炼分数 / 幻境终阶 / 工房等级 / 通关总数） | **没有**。就是"一个有名字、职业固定、免费到手的人" |
> | **酒馆佣兵** | 每天 3 个候选，金币雇佣；每日免费刷新 1 次，可付费重 roll | 有**稀有度**（普通/优秀/精锐/英雄），只影响"资质"（属性系数 1.00–1.15） |
>
> 三条关键决定：
> 1. **名角不带专属机制、也不带数值特权**。好处是不会出现"你喜欢的角色是废物"，
>    也不会因为角色强度把战斗内核搅乱——稀有度只存在于佣兵市场里。
> 2. **队伍有上限**（12 起，靠章节与工房扩张），满了要辞退，让"雇谁"成为决策。
> 3. **金币因此有了去处**：雇佣费 + 重 roll 费 + 上限扩张，补上了蓝图里"金币经济"的缺口。
>
> 名角名单、稀有度数值与名字生成器见 `app/src/data/companions.ts` 与 `app/src/data/hires.ts`，
> 逻辑在 `app/src/game/tavern.ts`；老档走 v8→v9 迁移，成员一个不丢。

FF14 的 Duty Support（信任/搭档）系统是这次设计的**钥匙**：
官方剧情里，你本来就是带着阿尔菲诺、阿莉塞、桑克雷德、雅·修特拉、于里昂热、埃斯蒂尼安、古·拉哈·提亚这些人下副本的。
所以"编队"这个概念在 FF14 里**不需要发明**，它就在那里。

- **账号轴（纵向）**：光之战士的 **19+ 战斗职业**，每职业独立等级、共用装备池、可切换
- **伙伴轴（横向）**：拂晓成员作为"固定职业的强力队友"，靠剧情/任务/好感解锁与强化
- **收集轴**：坐骑 / 宠物 / 九宫幻卡 / 乐谱 / 成就 / 称号 / 幻化 / 图鉴

### 决策二：养成深度从哪来？（FF14 没有天赋树）

wow-idle 的深度靠 **天赋树 + 套装 + 技能解锁**。FF14 **没有天赋树**，所以不能照抄。替代来源：

| 替代轴 | FF14 依据 | 建议用途 |
| --- | --- | --- |
| **职业量谱精通** | 各职业有专属 Gauge（黑骑暗血、武士剑气、龙骑龙血…） | 主养成：升级量谱解锁被动，**最像天赋树** |
| **特性(Trait)** | 官方升级自动获得被动 | 被动成长骨架 |
| **技能升级 / 技能选择** | FF14 等级解锁技能，且有"技能优先级" | 技能等级 = 放置游戏的技能树 |
| **魔晶石(Materia) 镶嵌** | 副属性定制、有上限(cap)与禁忌镶嵌 | ⭐ 最像"配装词条"，是**最容易做的深度系统** |
| **套装 / 幻化** | 副本套装、幻化柜 | 收集 + 属性 |
| **幻境武器(Relic)** | 跨版本的超长材料链 | ⭐ **长线至尊目标**（多阶段、跨内容、极耗时） |
| **生产/采集** | 8 生产 + 3 采集 | 资源链/经济层 |

**建议**：主养成 = `等级 → 特性 → 量谱精通`；配装深度 = `iLvl + 魔晶石`；长线 = `幻境武器链`。

> 💡 **官方背书**：8.0 的战斗系统重构引入了 **Evolved Mode**，官方定义是
> "offers **greater emphasis on job identity**"（更强调职业特色）。
> 也就是说 FF14 自己承认"每个职业应当有独特身份"——
> 这正是放置游戏"每个可培养单位必须有记忆点"的诉求，**可以直接引用为设计原则**。
> 反面教训同样明显：如果 20 个职业只差倍率，那就是失败设计。

#### 决策二的落地答案：职业放置化难度排行（来自 `01-jobs.md` §12）

`01` 用四个维度（资源可数化 / 循环可确定化 / 团辅可对齐化 / 空间依赖）给全部 23 个职业评了"放置化难度"。
**首批该做哪些职业，答案很明确：**

| 梯队 | 职业 | 为什么 |
| --- | --- | --- |
| **第一梯队（先做）** ⭐ | **WAR 战士、WHM 白魔、BLM 黑魔、MCH 机工、SMN 召唤、RDM 赤魔、SGE 贤者、BST 驯兽师** | 全是"单/双整数资源池 + 固定循环 + 无团辅或团辅极轻" |
| 第二梯队（可做） | DRK 暗骑、SAM 武士、RPR 死神、GNB 绝枪、PLD 骑士、MNK 武僧、DRG 龙骑、SCH 学者、PCT 绘灵 | 需要额外的组合状态或双相切换建模 |
| 第三梯队（暂缓） | BRD 诗人、DNC 舞者、NIN 忍者、VPR 蝰蛇 | 随机触发 / 组合输入 / 团辅对齐，需改用期望值模型 |
| 不建议正面还原 | **AST 占星**（抽卡+分发+星位对齐，最难） | 官方自己都在 6.0 后持续简化它 |
| 换个思路 | **BLU 青魔** | 不还原战斗，改做**"技能收集 + Build 配装解谜"**（收集 100+ 技能，选 24 个装配） |
| 特别推荐 | **BST 驯兽师** | 官方 7.56 新职业，TP 阈值 + **Inner Compass 天然是状态环**，且自带棋盘 roguelike 玩法 |

**可直接复用的 12 条机制映射**（完整 20 条见 `01-jobs.md` §12.3）：

| 编号 | FF14 机制 | 放置机制 |
| --- | --- | --- |
| M1 | 能量池累积（0→100，阈值解锁强技） | **资源条 + 阈值技能**，闲置时按 `资源/秒` 自动增长 |
| M2 | 层数堆叠 + 消费爆发（百合 3 层、查克拉 5 层） | **蓄力层数 → 一次大爆发**，离线积层、上线释放 |
| M3 | 固定 CD 爆发窗口（60s / 120s） | **技能轮转表**：按秒 tick + CD 队列（最稳的模型） |
| M5 | 连击链 Combo | **顺序解锁的伤害递增**，`combo[]` 表 + 断连判定 |
| M6 | 状态机循环（黑魔 Astral/Umbral、驯兽 Inner Compass） | **双/三态切换**（FSM），各状态产出与消耗不同 |
| M7 | 随机触发 proc（诗人 Repertoire） | **默认用期望值**（保证离线收益可预测），随机只做皮肤 |
| M8 | 充能式资源（以太超流 3 层） | **充能技能**：`charges` + `recharge_timer` |
| M9 | 方向指定 positional | **自动站位**，把方向指定降级为"熟练度被动" |
| M11 | 限时窗口内压缩技能数 | ⭐ **窗口内技能排程优化**——放置游戏**最有深度**的一层 |
| M12 | GCD(2.5s) / oGCD 二分 | **行动槽**：每 tick 1 个 GCD 槽 + 不定量 oGCD 槽（可直接沿用 2.5s） |
| M14 | 棋盘式 roguelike（破魔试炼场） | **关卡推进 + 局内 build**（Ephemeral Items / Beast Gear / Feed） |
| M19 | 极限技（团队共享能量） | **团队能量条 → 手动大招** |

> ⚠️ **M4 团辅（party buff）建议弱化或删除**。`01` 称官方已在 8.0 宣布删除团辅，
> 这一点在我的 `09` 中只找到"媒体称 Evolved Mode 移除 2 分钟爆发元"的**媒体报道级**证据，
> 引用时须降级为 ⚠️（详见 `09` §4.12）。但**方向是明确的**：删掉团辅能大幅降低复杂度。

### 决策三：战斗抽象到哪一层？

| 层级 | 内容 | 实现成本 | 建议 |
| --- | --- | --- | --- |
| L1 | 纯数值对撞（战力 → 胜负/耗时） | 低 | MVP 底线 |
| L2 | **职能三角**：坦克(仇恨/减伤) + 治疗(HPS/MP) + DPS，含暴击/直击、团辅爆发窗口 | 中 | ⭐ **主目标**，wow-idle 做到了这一层 |
| L3 | 完整机制模拟（分摊、踩塔、击退、无敌帧） | 高 | 用"机制标签"轻量模拟，不做逐帧 |

**建议 L2 + 机制标签**。理由：`02-combat-math.md` 会给出公式，但放置游戏的乐趣在"配置决策 + 数字增长"，
逐帧机制只会让战报变长、让玩家看不完。用"这个 BOSS 有【分摊】【击退】【DPS 检查】"这类标签做判定点缀即可。

## 4. 数值框架（草案）

### 4.1 章节与等级（已用官方数据校准）

**章节模板 = 一个资料片 = 10 级 + 120 iLvl + 固定内容配额**（数字全部来自 `data/content-plan.csv` 实测）

### 4.2 离线收益 —— **采用"派遣状态机"，不要"每秒流水"**

`08-wow-idle-architecture.md` §3.1 的源码结论推翻了一个常见假设：
**参考实现里根本不存在"主循环"**。全项目只有 4 处 `setInterval`，且全部只用于推进进度条；
没有任何"每 tick 产出金币/经验"的逻辑。它的放置本质是：

```
派遣（写入 startTs + durationMs + seed + 阵容快照）
   → 等待（期间什么都不算）
   → 收获（把 running 直接推成 ready，幂等发放奖励）
```

【事实】`engine.js:3007` 注释原文：
> 推进远征状态：到时的 running → ready（离线重开也会结算已流逝时间）

**这带来两个巨大好处：**
1. **离线收益无需任何专门计算**——进度是 `now - startTs` 的函数，重开页面时把 `running` 推成 `ready` 即可；
2. **天然防连点、天然防"离线最优"**——因为收益来自"事件的完成"而不是"时间的长度"，不存在 η（离线效率）这个旋钮。

**结论：FF14 Idle 采用同构设计。** 不写"离线 N 小时获得 X"的结算器，而是：

```
玩家配置：目标内容 + 队伍 + 消耗品 + 撤退点   →   派遣
产出：固定掉落 + 固定经验（与在线派遣完全一致）
离线只影响"A 到 B 之间经过了多少次可收获循环"
```

对应到 FF14 语义，就是官方的 **Retainer Ventures（雇员探险）/ 部队潜艇** —— 派出去，到点回来交货。

**若要引入"挂机流水"（如采集），再单独加一条低速率线**（参考实现也有第二条线：`tickGathers` 采集挂机），
但它必须**有上限且不与派遣竞争**，否则会退化成"挂机时长 = 收益"的劣化设计。

**8.0 的"每周自选进度"在此之上再叠一层**：每周给一个 `进度点数额度`，
玩家自由分配到任务/副本/FATE/前线，不同途径产出不同——这是"派遣"之上的**周期性资源分配**玩法。

### 4.3 iLvl 曲线 —— **已从官方数据实测出来，是线性的**

从官方 Lodestone 抓取的 369 条副本数据（见 `11-content-inventory.md`）推导：

```
等级：  ARR 15→50，其后每个资料片恰好 +10 级（51-60, 61-70, 71-80, 81-90, 91-100）
iLvl：  该资料片上限 = 230 + 130k      （230, 360, 490, 620, 750）
        该资料片下限 = 上限 − 120
衔接：  上一版上限 +10 = 下一版入门线（230→240, 360→370, 490→500, 620→630）
```

实测区间（4 人本）：

| 资料片 | 等级 | iLvl | 跨度 |
| --- | --- | --- | --- |
| 2.0 ARR | 15–50 | 42–90 | 48（异常：内容翻倍、曲线减半） |
| 3.0 HW | 51–60 | 100–230 | 130 |
| 4.0 SB | 61–70 | 240–360 | 120 |
| 5.0 ShB | 71–80 | 370–490 | 120 |
| 6.0 EW | 81–90 | 500–620 | 120 |
| 7.0 DT | 91–100 | 630–750 | 120 |

**⚠️ 关键设计决定：FF14 Idle 的数值曲线用线性，不要用放置游戏惯例的指数膨胀。**
理由：① 与官方真实节奏同构，玩家可解释；② 线性曲线让"卡关→提升→通关"的节奏可控；
③ 内容量（369 条）本身就能提供长线，无需靠数字爆炸撑时长。

三类内容的固定分层（以 Dawntrail 实测）：`4人本 630–750` / `极神 690–770 ≈ 零式 700–770 ≈ 天花板` /
`普通大型任务 ≈ 天花板−25` / `绝境战 无 iLvl 要求（强制等级同步）`。

**8.0 借鉴**：iLvl **绑定角色**（账号级），职业只决定技能与等级 → 避免"换职业要重新配装"的放置游戏坟场。

### 4.4 周期节奏设计 ⭐（放置游戏的骨架）

来自 `06-side-content-pvp.md` §7 对 FF14 全部有重置周期内容的整理。**这是蓝图里最容易做错、也最影响留存的一块。**

#### 四层节奏结构（照搬 FF14）

```
第 1 层｜无重置的离线生产线   ← 潜艇 / 雇员探险 / 岛屿庇护所 / 宇宙探索
第 2 层｜每日次数型           ← 任务轮盘 / 狩猎日榜 / Mini Cactpot / 挑战日志每日部
第 3 层｜每周上限型 + 清单型   ← 神典石周限 / 天书奇谭 / 每周挑战
第 4 层｜赛季级排行与奖励      ← PvP Series / 深层迷宫排行 / 破魔试炼场排行
```

这四层同时解决两个问题：**上线动力**（第 2/3 层）与**离线预期**（第 1 层 + 第 3 层的周上限）。

#### 周常必须区分三种性质（FF14 全都给了现成范例）

| 性质 | FF14 范例 | 放置化做法 | 优先级 |
| --- | --- | --- | --- |
| **① 硬上限型** | 神典石周限、藏宝图周限 | **每周收益上限** —— 防止数值一周内失控的核心阀门 | P0 |
| **② 任务清单型** | 天书奇谭、挑战日志 | **每周任务面板**（做完打勾） | P0 |
| **③ 定时开奖型** | **Jumbo Cactpot（周六 21:00 JST 开奖）** | **每周固定时点开奖** —— 回访率最高的一类 | P0 |

#### ⚠️ 必须改掉的 FF14 设定

| FF14 的做法 | 问题 | 应该怎么做 |
| --- | --- | --- |
| 每日重置 = 北京 **23:00** | 对上班族极不友好（睡前做的任务算"昨天"） | 改为**本地 04:00–05:00**（主流手游惯例） |
| 每周重置 = 周二 16:00（北京） | MMO 的一周对放置游戏**可能太慢** | 默认压到 **3 天**，可配置 |
| 赛季约 3–4 个月 | 放置游戏内容消耗快 | **6–8 周**一赛季 |
| 季节活动每年 1 次（现实节日） | 太稀疏 | 改为**游戏内历法**，每 6–8 周一次（6 倍频次） |

#### ⭐ FF14 最大的启示：它缺的正是放置游戏的主场

全表 50+ 项内容里，**只有"兽栏训练"是小时级（30 分钟恢复 1 次，上限 3 次）**。
其余全是日/周/赛季级。

> **结论：放置游戏应把主循环放在 15 分钟 – 4 小时区间**，
> 把日/周节奏留给"任务与上限"层。
> 换句话说：**FF14 做对的那部分（周上限、赛季、无重置产线）照抄；
> FF14 没做的那部分（小时级节奏）正是我们要补的主场。**

#### 另外两条可抄的机制

- **赛季末期解禁**：7.56 取消了 AAC Heavyweight 零式的周限奖励与周入场限制（末期让落后玩家追进度）。
  → 放置游戏**做，但只在赛季末 2 周**；全程开放会让周限失去意义。
- **过期作废**：PvP Series 奖励须在下季结束前领取，过期失效。→ 制造紧迫感，值得抄。

### 4.5 六个可直接复用的高价值机制

这六个机制在 FF14 中反复出现，且**与具体玩法解耦**，可移植到任何放置游戏（来自 `06` §9.6）：

| # | 机制 | FF14 出处 | 为什么值得抄 |
| --- | --- | --- | --- |
| 1 | **第三名累积补偿**（连续第 3 名 +10%，最高 +50%，第 1 名清零） | 前线 | 最优雅的连败保护，防止玩家因连续失利流失 |
| 2 | **分数取最近 N 次最佳** | 破魔试炼场（最近 3 次） | 降低单次运气影响，鼓励反复挑战而非"一次定生死" |
| 3 | **软重置**（进度清零，强化保留） | 深层迷宫 | 给卡关玩家出路，同时延长系统寿命 |
| 4 | **跨角色共享进度**（第一把做满，其余免费同步） | 幻影武器 | 大幅降低多角色重复劳动 |
| 5 | **难度档位自选**（三档 Degrees） | 破魔试炼场、Pilgrim's Traverse | 一套内容覆盖多种玩家，玩家自选风险/收益曲线 |
| 6 | ⭐ **离线待鉴定箱**（离线产出 → 上线鉴定 → 随机开箱） | 诅咒宝藏 / Accursed Hoard | **把"离线收益"变成"上线时的期待感"而不是纯数字** |

> 第 6 条尤其重要：它解决了"派遣制"最大的体验问题——
> 玩家回来只看到"+5000 金币"是无聊的，**看到"3 个待鉴定宝箱"才有开箱欲望**。

## 6. 项目骨架

### 6.1 先说技术选型：**不要照抄参考实现的技术栈**

`08` 的结论很明确——参考实现的**玩法设计**值得抄，但**工程实现**不值得抄：

| 参考实现的做法 | 问题 | FF14 Idle 应该怎么做 |
| --- | --- | --- |
| 自建 `__ns` 模块系统 + 手写拓扑序 | 无校验、值快照语义、无 tree-shaking | **标准 ESM + Vite**（TypeScript 可选但推荐） |
| 8,699 行的 `ui.js`（视图 + 应用层混在一起） | 无法协作/测试、162 个全局变量 | **拆成 `app/` + 各 Tab 一个 `views/` 模块 + store** |
| `data-action` + 234 个 `if` 的分发器 | 无法静态分析、分支顺序敏感 | **`ACTIONS[action]` 映射表**，未注册 action 打警告 |
| 全量 `innerHTML` 重绘 | 丢焦点、大列表卡 | **keyed diff**（Preact/lit 或自写 keyed 列表）；进度条直改 DOM |
| `battle.js` 8 个模块级可变全局 | 不可重入、难测试 | **显式 `BattleCtx` 对象** |
| 奖励用裸 `Math.random()` | 无法回放/审计 | **全部走注入式 RNG**，按用途 fork（`rng.fork('loot')`） |
| 三套战斗管线（副本/PvP/战场） | 维护三份 | **一个战斗内核 + 规则插件** |
| 无测试 | 全靠手测 | 至少覆盖：迁移、战斗确定性、经济守恒、内容一致性 |

### 6.3 从参考实现**直接照搬**的 14 条设计（`08` §10.1 摘要）

优先级最高的 6 条：

1. **派遣即结算 + 时间戳状态机 + 收获幂等** —— 放置闭环的核心范式，天然离线、天然防连点
2. **注入式 RNG + seed + 阵容快照 → 可复现战报** —— 回放不需要存日志，存档体积降一个数量级
3. **"门槛 + 优先级"的自动战斗技能 AI** —— 自动战斗可玩性的关键
4. **trace 事件流** —— 一份数据同时驱动动画、日志、战斗时长、回放
5. **存档完整性 + 备份 + 隔离区 + sequence 序列号** —— 低成本换来"不丢档"，`sequence` 是云同步必需品
6. **序列化裁剪（大日志出主档 → IndexedDB）** —— 放置游戏日志必然爆炸的标准解法

其余 8 条（数值当量预算、声明式 migrate、可插拔存储/广告降级、渲染错误隔离、掉落查询倒排、
单旋钮难度 `q`、文案与数据同表、1Hz tick 只改进度条）见 `08` §10.1。

## 8. 风险与合规 —— 这是本项目最大的风险，必读

完整依据见 `07-data-sources-licensing.md`（572 行，含条款原文与 URL）。**先说结论：FF14 同人放置游戏属于未被官方明确讨论过的灰区，且"非商业"并不等于安全。**

### 8.1 四条硬红线

| 红线 | 条款依据 | 对项目的约束 |
| --- | --- | --- |
| **① 禁止商业化（且定义极宽）** | 素材许可日文版：「利益の有無を問わず…対価、報酬、謝礼を受けること及び、宣伝や広告に利用すること」 | **打赏、爱发电、Patreon、Ko-fi、赞助、付费 DLC、内购、广告位、把游戏当作自己其它产品的宣传入口——全部禁止**。注意是"不问是否盈利" |
| **② 禁止素材二次分发与实质性修改** | 素材许可英文版（只能与**其它 FF14 素材**混剪，暗示不得混第三方素材）；日文版"不得过度加工" | **不能把 FF14 的贴图/模型/UI/图标打进游戏包**；也不能"改一改再用" |
| **③ 禁止数据挖掘 / 反编译 / 衍生作品 / 私服** | EU 版 User Agreement §2.5（禁止 mine）、§2.6/2.7（禁止反编译与衍生作品）、§2.4（禁止私服）；日文版「禁止事項」含「解析」「リバースエンジニアリング」 | ⚠️ **这一条和我们的 `data/*.csv` 直接相关**——数据本身来自官方公开页面（属公开信息，风险较低），但**技能效力等来自第三方 datamining 仓库的数据风险较高**，建议只用官方公开可见的字段 |
| **④ 音乐已信托 JASRAC（2026-05-07 起）** | FF14 全部原创乐曲著作权信托给 JASRAC，网络使用须走与 JASRAC 签约的 UGC 服务 | **绝对不要内嵌 FF14 原曲/BGM**。连"带 FF14 BGM 的视频发到 X"都被点名不允许 |

### 8.2 一个容易被忽视的点

SE 官网《著作権について》明确：即使是著作权法允许的私人复制，
**只要放到互联网上，未经权利人许可即侵害"公众送信权"——非营利个人主页也不例外，
加 ID/密码访问限制也不能免除违法性。**
且素材许可本身是**可撤回**的，SE 可"以其完全裁量"要求撤下。

### 8.3 因此，本项目的合规定位建议

```
✅ 只借用"世界观 / 名词 / 系统概念"的最低限度表达（设定与玩法本身不受著作权保护）
✅ 100% 自制美术，或使用 CC0 / OFL / 明确可商用的素材
✅ 完全免费、无任何变现入口（连"请我喝咖啡"链接都不要放）
✅ 显著位置同时放商标声明 + 版权声明，明确"非官方同人作品，与 SQUARE ENIX 无关"
✅ 不内嵌任何 FF14 音乐/音效；如需音乐，用 CC0 音源
✅ 准备好被要求时立刻下架（这应当被视为项目预设的结局之一）
❌ 不用 FF14 素材、不做变现、不碰 datamining 私有数据、不碰私服/服务器模拟
```

> ⚠️ 一旦被论证为"复刻游戏内数值系统 + 完整游戏流程"，可能落入"衍生作品"甚至"游戏模拟"的解释。
> **建议：先把它当技术练手与同人创作，不要以"能上线运营"为前提做规划。**
> 若要认真商业化，正确路径是做一个**原创 IP 的同类放置游戏**，只借鉴 FF14 的系统设计经验。

### 8.4 风险光谱与同形态先例（`07` §4、§6）

```
🟢 原创 IP（只借鉴玩法结构）  →  🟠 借用名词体系  →  🔴 同人页游 + 变现  →  🔴🔴 私服/服务器模拟
```

| 发现 | 意义 |
| --- | --- |
| **`Toxocious/FFXIV-Idle`（GitHub）** —— 自述 "An incremental game based around Final Fantasy XIV" | ⭐ **最直接的同形态先例，未见任何下架/警告记录**。说明"FF14 主题的放置游戏存在于 GitHub"本身并不招致立即行动 |
| **Melvor Idle 案**（被 Jagex 收编） | ⚠️ **不能拿来论证"FF14 放置游戏没问题"**——它与 RuneScape 共享的是**玩法结构而非作品表达**，且是**原创 IP**。用它类比属于偷换前提 |
| **PlayerScope 事件（2025-06）** | SE 会对**隐私/骚扰**类问题立刻出手；但对同人创作的选择性容忍度明显更高 |

> 修正我先前的说法：**"FF14 同人放置游戏没有先例"是不准确的**——
> 先例存在（`Toxocious/FFXIV-Idle`），只是**没有被官方明确讨论过**，仍属灰区。

### 8.5 ⚠️ 数据源的法律分层（**直接影响本项目的 `data/` 计划**）

`07` §3 的核心论点：**"API 代码 / API 条款 / 数据的著作权"是三件不同的事，"调得通"≠"能用"。**

| 我们的数据 | 来源 | 风险 | 处置建议 |
| --- | --- | --- | --- |
| `duties.csv` / `dungeons.csv` / `content-plan.csv`（副本名、等级、iLvl 门槛） | **官方 Lodestone 公开页面** | 🟡 中（事实性关系 + 抓取 Lodestone 触及 EULA 3.2 Disruption） | 限速抓取、只用必要字段、**自行重写数据结构与字段名**、不搬运官方描述文本。**优先考虑手工整理** |
| 技能效力 / 伤害公式 / 装备成长曲线（来自 **XIVAPI / ffxiv-datamining**） | 社区数据挖掘 | 🟠 **高**（EULA 2.5 挖掘 + 2.7 衍生） | ⚠️ **不要打包 datamining 数据表**。数值体系应**自行设计**（我们本来就采用线性曲线，不必抄官方公式） |
| 市场板数据（**Universalis**） | **玩家上报**，非解包 | 🟢 **全清单唯一法律干净项** | 如需经济数据，优先用它；遵守限流、署名、给链接 |
| Wiki 玩家撰写文本 | 社区 Wiki | 🟡（**CC BY-SA 传染**） | 若将来闭源/商业化 → **不要引用**；否则署名 + 同许可 |

> 🔴 **结论**：本项目应定位为**"只借名词与玩法结构，数值与文本全部自研"**。
> 好消息是——我们的设计（线性 iLvl 曲线、派遣状态机、自研职业机制映射）**本来就不依赖官方公式数据**，
> 所以这条限制**几乎不影响设计蓝图，只影响数据采集方式**：
> **用 Lodestone 公开信息做"内容清单"，用自研数值做"游戏平衡"。**
>
> XIVAPI v2 的技术红利（`schema` + `version` 双锚点可 pin）确实诱人，但**技术可行性不等于法律可行性**。
