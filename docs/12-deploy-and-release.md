## 一、先回答那个最要紧的问题：仓库该叫什么名字

**随便叫什么都可以。** GitHub Pages 的项目站点地址是：

```
https://<你的用户名>.github.io/<仓库名>/
```

只要仓库名是合法的（字母、数字、`-`、`_`、`.`），任何名字都能做静态站，**不需要为了部署改任何配置**。
本项目所有资源引用都是相对路径（`vite` 的 `base: './'`），放在子路径下和放在根目录下都能跑
——而且这件事有测试守着：`app/tools/pages_test.py` 就是专门按 `/ff14-idle/` 这种子路径
起服务器跑一遍的。

两个建议：

| 情况 | 建议 |
| --- | --- |
| 一般情况 | 像本项目这样叫 `ff14idle`，地址就是 `https://<用户名>.github.io/ff14idle/` |
| 想让地址没有仓库名（`https://<用户名>.github.io/`） | 仓库必须**恰好**叫 `<你的用户名>.github.io`。一般不必要 |

其他要点：

- **必须是 Public**。私有仓库要用 GitHub Pages 得付费（GitHub Pro 及以上）。
- 仓库建成**空的**就行（不要勾 README / .gitignore / license），否则第一次推源码会冲突。
- 仓库名和游戏标题无关；游戏标题写在 `app/index.html` 与 `app/public/manifest.webmanifest` 里。
- 提交署名用的是**你这台机器上已经配好的 git 身份**，脚本不会硬写一个名字进去。
  想换：`git config --global user.name "..."` / `git config --global user.email "..."`。

## 二、一次性设置（只做一遍，约 2 分钟）

1. 在 GitHub 上新建一个 **Public** 空仓库，名字比如 `ff14-idle`。
2. 双击 `ff14-idle/一键发布.bat`。
   第一次运行会问你仓库地址，格式：
   ```
   https://github.com/你的用户名/ff14-idle.git
   ```
   填一次就会被记在 `.deploy.json` 里，以后不用再填（这个文件在 `.gitignore` 里，不会进仓库）。
3. 脚本跑完之后，去仓库 **Settings → Pages**：
   - **Source** 选 `Deploy from a branch`
   - **Branch** 选 `gh-pages`，目录选 `/ (root)`
   - Save
4. 等 1–2 分钟，打开 `https://你的用户名.github.io/你的仓库名/`。

> 第 3 步必须做一次：GitHub 不会自动知道要发布 `gh-pages` 分支。
> 之后再发版就**只需要双击**，不需要再碰设置。
>
> 判断这一步做完没有，最快的办法是直接访问那个网址：
> **404 = 还没设置**（或者刚设置完还在构建，等 1–2 分钟）；**能打开 = 已经生效**。

## 三、平时怎么更新一版

```
双击  一键发布.bat
```

脚本会依次做六件事，任何一步失败都会停在原地并说明原因（不会把半成品推上去）：

| 步骤 | 干什么 | 为什么 |
| --- | --- | --- |
| 1 | 找 node / python | 本机 node 由 nvm 安装，并不在 PATH 上，脚本会自己去找 |
| 2 | 读/升版本号 | 页脚和 `version.json` 都要用它 |
| 3 | `tsc --noEmit` + 两次 `vite build` | 类型检查挡在前面，再出差错就晚了 |
| 4 | **产物自检** | 检查单文件里没有外部 JS/CSS、多文件版引用的资源都在、`version.json` 已生成 |
| 5 | 确定仓库地址 | 从 `.deploy.json` 读，读不到才问 |
| 6 | 推 `main`（源码）+ 推 `gh-pages`（产物），并核对远端提交号 | 发布完必须能确认"远端真的收到了" |

可选参数（在命令行里加，双击时不加就是默认行为）：

```powershell
python tools/deploy.py --bump patch     # 先把版本号 0.1.0 → 0.1.1 再发布
python tools/deploy.py --dry-run        # 只构建 + 自检，不推送（改完先看看能不能过）
python tools/deploy.py --skip-source    # 只更新网站，不推源码
python tools/deploy.py --remote https://github.com/名字/仓库.git   # 换仓库
```

## 四、手机怎么玩

1. 手机浏览器打开 `https://forever985.github.io/ff14idle/`
2. **iPhone（Safari）**：底部分享 → 「添加到主屏幕」
   **Android（Chrome）**：右上菜单 → 「添加到主屏幕 / 安装应用」
3. 从主屏图标点开就是全屏、没有地址栏，和装了个 App 差不多。

图标是项目自绘的（`app/public/icon.svg`），要换只改这一个文件，然后跑：

```powershell
python app/tools/gen-icons.py     # 重新生成 192/512/180/32 四个 PNG
```

### 手机上"更新了没生效"怎么办

手机上加到主屏之后**没有刷新按钮**，也做不了强刷。所以页面自己会管这件事：

- 页脚常驻显示 **版本号 + 构建时间**（例如 `v0.1.0 · 2026-09-17 15:28`）——这是"我现在跑的是哪一版"的唯一依据；
- 页面启动时、以及每次从后台切回前台时，会带时间戳去取一次 `version.json`，
  发现线上构建和自己不是同一次，就在底部弹一个 **「有新版本，点这里更新」** 的按钮。
  点它会用一个新网址重新加载（绕开 GitHub Pages 的缓存），不是普通的 `reload()`。

GitHub Pages 自身对 HTML 有大约 10 分钟的缓存，所以刚发布完可能还要等一会儿才会提示。

## 五、存档：会在版本之间保留，但有两条硬规矩

存档在浏览器的 `localStorage` 里，**换版本不会丢**（同一域名下就一直有效）。
但下面两件事必须守住，否则要么丢档、要么旧档读不进来：

1. **只要改了存档结构，就必须加一段迁移。**
   迁移写在 `app/src/core/save.ts` 的 `migrate()` 里，格式是 vN → vN+1 逐级升级，
   当前已经到 v7。只加字段、不改含义的话也要显式补默认值。
2. **不要改 `localStorage` 的 key，也不要换域名。**
   key 换了、或者从 `xxx.github.io` 换到自定义域名，玩家的存档就是另一个世界了
   （不是丢了，是"看不见了"）。
   存档里带摘要校验，所以**手改存档内容会被判为损坏**——这是故意的：
   损坏时页面会提示，并尝试从备份恢复，而不是静默重开。

### ⚠️ iPhone 上有一个真实风险，必须知道

Safari 的智能防跟踪（ITP）会限制"脚本可写存储"：**一个站点如果连续 7 天没有交互，
它的 localStorage 可能被清掉**。对放置游戏来说这正好是最容易中的一枪。

务实的对策（按推荐顺序）：

1. **每周至少点开一次游戏**（哪怕就点一下），计时器就会重置；
2. 定期用游戏底部的 **「导出存档」** 存一份到备忘录/文件里，出事能导回来；
3. 主屏安装的 Web App 通常被认为"在用"，一般不受这条限制——但没有官方文档
   把这件事写死，所以别把它当成唯一保险。

> 如果你觉得这条风险不能接受，下一步可以做成"云存档"（GitHub Gist / 自建小后端），
> 那属于新功能，需要单独排期。

## 六、为什么是这套发布方式（而不是 GitHub Actions）

也考虑过 GitHub Actions：push 之后由 CI 构建并发布。这里没选它，原因有三个：

| | 双击脚本 + `gh-pages` 分支（本方案） | GitHub Actions |
| --- | --- | --- |
| 需要网页上做什么 | 只需一次性设置 Pages 来源 | 需要一次性设置 Pages 来源 = GitHub Actions |
| 构建发生在哪 | 你自己的电脑，和平时跑测试的同一套环境 | GitHub 的机器，Node 版本/依赖要另外对齐 |
| 出问题怎么查 | 停下来把错误打在你眼前 | 要去 Actions 页面翻日志 |
| 仓库里存了什么 | `main`=源码，`gh-pages`=产物，一眼能看懂 | 多一套 workflow 配置要维护 |

另外，`gh-pages` 分支每次都是"从零重建 + 强制推送"，所以它永远只有一条提交，
不会像某些方案那样把仓库体积越滚越大。

**代价**：发布必须由你双击触发，不能"改完 push 就自动上线"。
想要自动化的时候再加 Actions 也不冲突（两者可以并存，指向同一个 `gh-pages`）。

## 七、这次部署踩到的坑（都属于"很容易再踩一次"）

### 1. git 把对象写坏了，但提交却"显示成功"

症状非常迷惑：`git commit` 打印了提交信息，紧接着以退出码 128 失败：

```
error: inflate: data stream error (incorrect data check)
error: corrupt loose object '7528ca75...'
fatal: unable to read 7528ca75...
```

`git fsck` 会告诉你有一堆松散对象坏了。**这是偶发的**，实测 4 次里：

| 配置 | 干净 |
| --- | --- |
| 带 `-c core.fsync=all` | 2 / 2 |
| 不带 | 1 / 2 |

也就是说 fsync **能减少但不能消除**（后来又亲眼见到一次带 fsync 仍然写坏）。
所以真正靠得住的不是某个参数，而是"**写完之后校验，坏了就重建**"：

| 环节 | 兜底做法 |
| --- | --- |
| 写对象 | `-c core.fsync=all`（减少概率）+ `-c core.autocrlf=false`（顺带消掉一百多行换行警告，不然真报错会被淹掉） |
| 打包 | `-c pack.threads=1`（打包只用一条线程） |
| 提交后 | `git fsck` **校验整个对象库**；不干净就删掉 `.git` 重新提交（源码都在工作区，`.git` 只是派生数据，重建无损） |
| 推送时 | 失败自动重试最多 3 次；推完用 `git ls-remote` **核对远端提交号** |

> 实测这条链路真的救过场：一次完整发布里，源码推送第 1 次因
> `remote unpack failed: index-pack abnormal exit` 失败，重试后成功并核对通过。
> 如果没有这层兜底，你双击一次就会看到一个莫名其妙的失败。

### 2. `detected dubious ownership`

仓库目录的属主和当前用户不一致时（目录是管理员身份创建的就会这样），
git 会用一句很难懂的话拒绝一切操作。脚本统一带 `-c safe.directory=*`，
只对当次调用生效，**不去改你全局的 git 配置**。

### 3. 记事本写出来的 JSON 带 BOM

`.deploy.json` / `package.json` 如果被记事本编辑过，开头会多一个 BOM，
`json.loads` 直接抛异常。症状是"我明明填了仓库地址，脚本每次还问我一遍"。
所以读 JSON 一律用 `utf-8-sig`。

### 4. `.bat` 里不能写中文

`cmd.exe` 按系统 OEM 代码页（本机是 GBK）读 `.bat`，UTF-8 的中文会变乱码甚至破坏语法。
所以 `一键发布.bat` 是**纯 ASCII** 的，所有中文提示都由 Python 打印
（Python 源文件是 UTF-8，脚本开头会把控制台切到 65001）。
同理，`.ps1` 也必须纯 ASCII —— 这个坑项目里早就踩过一次，见 `app/README.md` 第七节。

### 5. 重建 `.git` 之后，第二次发布推不上去

链条是这样的：本机 git 偶尔写坏对象 → 脚本删掉 `.git` 重新提交 → 于是本地出现一个
**全新的根提交**，而远端 `main` 上已经有上一次的提交 → 两者没有共同祖先 →
推送被拒（`non-fast-forward`）。症状是"第一次发布成功，第二次怎么说都不让推"。

修法：每次提交**之前**先 `git fetch` 一次远端 `main`，如果那条提交还不在本地历史里，
就把本地分支指到它，然后在它之上提交（`sync_with_remote()`）。这样推送永远是快进，
而且**不会丢掉远端已有的历史**——比一上来就 `--force` 安全得多。

顺带把"被拒"的报错换成了可操作的提示：远端有你没有的提交时，脚本会明确告诉你
要么 `git pull --rebase`，要么自己决定要不要 `-f`，而不是让你对着
"请检查网络与仓库权限"发呆。

### 6. 删 `.git` 删不干净 → 重试三次都是同一个错

修坏对象时要删掉整个 `.git`。但 `.git` 里有**只读文件**（Windows 上 git 会给部分文件
加只读属性），`shutil.rmtree` 会中途失败，留下一个"半死不活的 `.git` 目录"。
接着每条 git 命令都报 `not a git repository`，而 `if not .git.exists()` 又因为目录还在
而跳过了重新 init —— 于是三次重试全是同一个错，看起来像"根本修不好"。

修法（`wipe_git()`）：先清只读属性再删；删不掉就**改名挪走**（改名比删除更容易成功）；
最后再确认一次 `.git` 真的没了，没删掉就直接报错让你手动处理，而不是继续重试。

### 7. `gh-pages` 必须强制推送

`gh-pages` 每次都是"从零重建 + 一条提交"，和远端已有的那条提交没有共同祖先，
**永远不可能快进**，所以必须 `-f`。

这个 `-f` 在我重构推送函数时被漏掉了，症状是"第一次发布成功，第二次怎么都推不上去、
报 non-fast-forward"——排查时特别容易怀疑到权限或网络上去。
现在 `git_push(..., force=True)` 只给 `gh-pages` 用，`main` 依然是普通推送（保护你的历史）。

## 八、发版检查清单

改完东西准备发布时，照这个顺序走一遍：

- [ ] 改过存档结构？→ 已经在 `save.ts` 里加了迁移
- [ ] 跑一遍 `powershell -File app/tools/run-tests.ps1 -All`，看到 `RESULT: ALL PASS`
- [ ] 想升版本号？→ `--bump patch`（改了玩法）/ `--bump minor`（加了系统）
- [ ] 双击 `一键发布.bat`
- [ ] 手机上打开网址，看页脚版本号是不是刚发布的那一版
- [ ] 如果没变：等 10 分钟（Pages 缓存），或者点页面底部弹出的「有新版本」按钮
