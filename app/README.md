# 艾欧泽亚放置（FF14 Idle）

> 一款基于《最终幻想14》世界观的**非商业同人放置游戏**。
> 架构与设计来自 `../docs/10-design-blueprint.md`，数值、文案与**全部图标**均为自研。

## 界面（对标 Melvor Idle / 银河奶牛放置）

采用「**左侧常驻导航 + 顶部资源条 + 内容区**」的信息架构：

```
┌──────────┬──────────────────────────────────────────────┐
│ 🚀 派遣 ① │  拂晓血盟 · 第1章      💰12,800 📦5 🚀1 ⏱0 ✨+23% │
│ 🎲 试炼   ├──────────────────────────────────────────────┤
│ 🗼 无尽塔 │                                              │
│ 👥 队伍   │              内容区（卡片 / 进度 / 战报）        │
│ 🎒 背包 ③ │                                              │
│ 📅 周常   │                                              │
│ ✨ 幻境   │                                              │
│ 🏝️ 工房 ① │                                              │
│ 📜 战报   │                                              │
└──────────┴──────────────────────────────────────────────┘
```

- **图标全为手写内联 SVG**（`src/ui/icons.ts`，60+ 个）——既保证风格统一，也符合
  `docs/07` 的法务要求（不引入来源不清的素材）。随 `currentColor` 自动适配主题色。
- **悬停说明**：任何带 `data-tip` 的元素（资源条、职能标签、装备属性、棋盘节点、导航项）
  都会弹出说明，鼠标跟随并自动避让屏幕边缘。
- **键盘可操作**：`1`–`9` 直接切页，`Esc` 收起说明；按钮有 `:focus-visible` 焦点环。
- **数字反馈**：金币/箱子/可收获数变化时，数值会「跳一下并变亮」——放置游戏的核心快感是
  "看着数字涨"，涨的那一刻必须看得见。
- **导航角标**：有待办时（可收获、空闲装备、可领奖、工房产出）在导航项上显示数字并轻微脉动。
- **禁用即给出原因**：如"队伍还在外面，回来后才解锁战报"。
- **空状态给"下一步做什么"**，而不是干巴巴的"暂无"。
- **进度条**：内描边 + 斜纹 + 高光；到期时整条微微呼吸，提示"可以收了"。
- **面板**：统一的标题竖条 + 内高光 + 入场淡入；卡片悬停轻微抬起。
- **深浅主题**：默认**跟随系统**，顶栏右上角可手动切换（切过之后记住选择）。
  实现上有一条硬规矩：`styles.css` 的规则里**只允许出现 `var(--x)`**，不许再写颜色字面量——
  否则新主题一开就花。淡色系用 `rgb(var(--gold-rgb) / .16)` 这种"通道 + alpha"写法，
  换主题只改通道值，一整族透明度都不用重写；`--hl-rgb` 在浅色下从白翻成黑，
  于是所有"提亮"自动变成"压暗"。
  验收方式也很直白：`ui_shot.py` 会切到浅色，再检查 `.panel/.card/.topbar/.nav/.btn/.tag`
  里有没有哪个元素还是深色底。
- **动效有统一节拍**：动效时长/缓动全部收敛到 `styles.css` 的 `:root` 令牌
  （`--t-fast` 悬停 / `--t-base` 状态切换 / `--t-slow` 面板与进度条 / `--t-pop` 数值跳动），
  没有任何组件再写裸时长——否则同一个"悬停"在按钮上 .15s、在卡片上 .08s，快慢不齐就是
  "看起来不够精致"的常见来源。`--ease-back` 只给"数字跳一下"用。
- **无障碍**：`prefers-reduced-motion` 下自动关闭全部动效；按钮有 `:focus-visible` 焦点环。
- **总览表**：队伍页顶部一屏横向对比所有成员（等级/装等/生命/效力/精通/幻境/经验），
  避免 6 张详情卡堆成长页面后无法比较。
- **副本筛选**：一个章节有 13–31 个副本，全平铺时手机上要滚 **3700px** 且分不清主次。
  改为筛选胶囊「**待推进** / 已通关 / 全部」，默认只看待推进，并给下一个副本打上「下一步」标记
  —— 派遣页因此从 1486px 压到 **900px 以内**。
- **响应式**：≤820px 时侧栏折叠为顶部横向图标条；`tools/ui_shot.py` 会在 420px 宽度下
  实测并断言"无横向溢出、无元素越界"。
- **手机上像 App**：`public/manifest.webmanifest` + 自绘图标 + `theme-color` +
  `apple-mobile-web-app-capable`，加到主屏后从图标点开是全屏无地址栏；
  底部留了 `env(safe-area-inset-bottom)`，手势条不会压住内容。
- **版本可核对**：页脚常驻显示 `v0.1.0 · 构建时间 · git 短哈希`。手机上没法强刷，
  这一行就是"更新到底生效没有"的唯一依据；线上有新构建时页面会自己弹「点这里更新」。
- **存档备份提醒**：手机浏览器（尤其 iOS Safari 的 ITP）可能清理本地存储，
  连续一段时间没交互就可能被清掉——对放置游戏正好是最容易中的一枪。
  所以存档超过 6 天没导出就弹一条提示，一键导出 JSON；点「稍后」安静 3 天，
  新号前 2 天不打扰。导出会记录时间（存档字段 `lastExportAt`，v8 迁移补的默认值）。

> 想看效果不用跑起来：`screenshots/ui-*.png`（桌面逐屏）与 `ui-mobile-*.png`（窄屏）
> 都是 `tools/ui_shot.py` 自动截的图。

## 一、怎么跑起来

技术栈：**ESM + TypeScript + Vite**（无框架，零运行时依赖）。

```powershell
# 0) 本项目所在机器没有把 node 加进 PATH，需要先指到 nvm 的 node
$env:PATH = "C:\Users\18405\AppData\Local\nvm\v22.12.0;" + $env:PATH

cd "E:\deepseek harness\ff14-idle\app"

# 1) 首次安装依赖（已装好，可跳过）
npm install --registry=https://registry.npmmirror.com

# 2) 开发模式（热更新）→ http://127.0.0.1:5273/
npm run dev

# 3) 或：生产构建 + 本地预览 → http://127.0.0.1:4173/
npm run build
npm run preview -- --port 4173
```

### ✅ 双击就能玩（单文件构建）

```powershell
npm run build:single
# 产物：dist-single/index.html（约 146 KB，JS/CSS 全部内联，零外部 JS/CSS 引用）
# 直接双击打开即可，无需服务器
```

原理：普通 `dist` 是原生 ES Module，浏览器在 `file://` 下会以 CORS 为由拒绝加载**外部**模块脚本；
`build:single` 改用 **IIFE（传统脚本，非 module）** 并内联全部资源，从而绕开该限制。
两种构建并存，按需选用：

| 命令 | 产物 | 用途 |
| --- | --- | --- |
| `npm run build` | `dist/` | 部署到静态托管（GitHub Pages / Cloudflare Pages / Vercel 等） |
| `npm run build:single` | `dist-single/index.html` | **单个 HTML 文件，双击即玩、可随意分发** |

> 另有 `npm run dev`（热更新，端口 5273）与 `npm run preview`（预览构建产物，端口 4173）。

### 🚀 发布到网上（手机也能玩）

**双击仓库根目录的 `一键发布.bat`** 即可：它做类型检查 → 两次构建 → 产物自检 →
推源码到 `main` → 推产物到 `gh-pages`，最后把可点的网址打出来。

```powershell
python tools/deploy.py --dry-run     # 只构建 + 自检（推荐改完先干跑一次）
python tools/deploy.py --bump patch  # 先升版本号再发布
```

页面改不动、或者手机上没生效时，先看 `../docs/12-deploy-and-release.md` —— 那里写了
Pages 的一次性设置、版本号提示更新的机制、以及存档在 iPhone 上的真实风险。

### 破魔试炼：为什么它是第二个玩法轴

官方原型是 **7.56 新增的 Crucible of the Unbroken**（驯兽师专属单人玩法）。
它与副本派遣的区别在于**引入了资源管理决策**：

| | 副本派遣 | 破魔试炼 |
| --- | --- | --- |
| 血量 | 满血进场 | **跨节点继承、不自然回复** |
| 决策 | 选队伍与副本 | 何时用道具、**要不要继续冒险** |
| 结算 | 一次性 | 打到哪算哪，**放弃也按进度给分** |

实测难度曲线（`tools/trial_test.py` 的难度探针）：

```
15 级无装备队伍   → 平均推进 10.6 / 12 格，零通关（卡在守关者）
55 级队伍         → 6/6 通关
```

即：**天花板可达，但需要成长才能触及**。

### 职业量谱精通：为什么需要它

蓝图 §2 决策二指出：wow-idle 的养成深度靠天赋树，而 **FF14 没有天赋树**。
本作从官方每个职业都有的「量谱」取形，做成 4 节点的小树：
`T1a / T1b（二选一）→ T2 → T3 顶点`，于是**同一职业内部也要做路线选择**。
数值直接进入战斗快照（减伤 / 效力 / 治疗 / 生命 / 爆发加成 / 资源累积），
并且是**金币回收口**——MVP 之前只有产出没有消耗。

### 周期节奏设计（重要）

依据 `../docs/10-design-blueprint.md` §4.4：

- ⚠️ **没有照抄 FF14 的每日 23:00（北京）重置** —— 那对上班族极不友好
  （睡前做的任务会被算成"昨天"）。本作改为**本地 04:00**，与主流手游一致。
- 每周重置改为**本地周一 04:00**，键按此切分；`core/time.ts` 里所有周期函数都接受
  `resetHour` 参数，可整体调整。
- 周期函数有**边界测试**覆盖（周一 03:00 / 05:00 这类临界点），见 `tools/cadence_test.py`。

### 工房：离线产线为什么必须装"阀门"

离线产线是放置游戏最容易做坏的地方——**没有上限，最优策略就是永远别上线**。
所以这里刻意装了两道阀门（依据 `06-side-content-pvp.md` §7.4
「**周上限是数值策划的锚**」）：

| 阀门 | 作用 |
| --- | --- |
| **硬性储存上限**（1 级 8h → 5 级 24h） | 超过上限直接停产。挂 20 小时也只按 8 小时结算（测试有专项断言） |
| **连续收获加成 Groove** | 按时回来领 +10%/次（上限 +50%）；**一旦溢出则归零** → 「经常回来」比「挂很久」更划算 |

产出物是**待鉴定箱**而不是直接给数字（蓝图 §4.5 机制 6）：
把"离线收益"变成"上线开箱的期待感"，而不是结算弹窗上的一个数。

### 无尽塔：把"软重置"做成成长而不是惩罚

官方深层迷宫（死者宫殿 / 朝圣者之路）有三个标志性机制，本作全部采纳：

| 机制 | 本作落地 |
| --- | --- |
| **独立等级** | 进塔后从 **1 级**重新成长（每层 +1 级，每级 +6% 属性），与外面的等级无关 |
| **软重置** | 倒下或撤退都清零进度，但**塔之记忆永久累积**（每到达 1 层 +1%，上限 +150%）→ 每次攀爬都比上次更强 |
| **待鉴定箱** | 每 3 层产出 1 个，结算时一次性开出装备（把它变成"结算时的期待感"） |

**节奏**（界面上有"接下来 6 层"预览条，让"再爬几层"变成可规划的决定）：

```
每 10 层 = 层主（强度 1.8 倍）   每 5 层 = 休整层（回复 20% 生命）   每 3 层 = 待鉴定箱
5/15/25 休整，10/20/30 层主（层主层不重复当休整层）
```

**难度实测**（战斗内核用期望值，所以墙是精确的）：

```
15 级无装备队伍 → 19 层（卡在第 20 层层主）
55 级队伍       → 49 层
```

墙能靠成长越过（19 → 49），这正是想要的结构。

## 五、测试与验证

推荐用**自带服务器生命周期**的运行器（后台常驻服务器会在会话边界被回收，
导致"服务器意外关闭"）：

```powershell
powershell -File tools/run-tests.ps1 -All
powershell -File tools/run-tests.ps1 -Tests smoke_test,relic_test
powershell -File tools/run-tests.ps1 -All -NoBuild -SuiteTimeoutSec 300
```

运行器有三道保护：**构建新鲜度闸门**（`src/` 比产物新就自动重建）、
**每套件超时**（默认 180s，超时判 `TIMEOUT` 而不是无限等待）、
**残留浏览器清理**（只清 Playwright 的临时 profile）。

也可以单独跑（需自行先启动 `vite preview`）：

```powershell
python tools/smoke_test.py       # 26 项：渲染 / 派遣 / 离线结算 / 收获 / **不丢档** / v7→v8 迁移 / 备份提醒

python tools/relic_test.py       # 22 项：幻境武器（接线 / 跨系统门槛 / 替换 / 终阶加成 / 持久化）
```

## 七、踩过的坑（值得记住的 14 个）

### 1. ⚠️ 摘要把"共享引用"误判成环 → 打完副本就静默丢档

`canonicalize` 最初用全局 `WeakSet` 记录访问过的对象来防环。
但 `applyResult` 会把 `expedition.result.loot` 里的**同一批对象**推进 `state.inventory`，
于是状态图里存在**共享引用（非环）**：

- 签名时：第二次出现的引用被写成 `null`
- 验证时：存档经过 JSON 往返，共享关系消失、变成两份完整对象
- 结果：**摘要必然不匹配 → 校验失败 → 游戏静默重开**，玩家第一次打完副本就全档丢失

修法有三层：① 只用**祖先栈**检测真环（摘要必须是 JSON 内容的纯函数）；
② 入包时克隆 loot（不留别名）；③ 摘要不匹配但结构完好时**接受并重新签名**，
而不是丢档（单机本地存档：可用性 > 防篡改）。

> 教训：这个 bug 躲过了 6 个测试套件，因为**没有一个测试在"收获之后"再刷新页面**。
> 现已把「收获 → 保存 → 刷新 → 状态存活」写进 `smoke_test.py` 作为永久回归项。

### 2. 后台常驻服务器会被会话边界回收

表现为"服务器意外关闭"。改成 `tools/run-tests.ps1` **自带服务器生命周期**
（启动 → 跑测试 → `taskkill`），不再依赖长驻进程。

### 3. 依赖"别处已完成"的重置守卫 → 偶尔永不触发

无尽塔赛季重置最初写成 `if (weekChanged || !season.key) refreshTowerSeason(...)`。
问题：**若周重置已在别处（1Hz tick）完成，赛季就永远不会再同步**——
测试里手动把赛季键改成过期值后调用 `cadence()`，`weekChanged` 为 false，重置被跳过。

修法：改成**无条件调用幂等的 `refreshTowerSeason`**（函数内部只在 key 变化时重置）。
教训：重置逻辑要**自己判断该不该重置**，不要依赖调用方传入的"是否发生了变化"。

### 4. 状态守卫写反 → 整个玩法通过界面玩不了

破魔试炼的 `renderTrialTab` 守卫写成 `if (!run || run.status !== 'finished')`，
把 `running` 也匹配进了"组队页"分支。后果：**开始试炼后界面仍停在组队页**，
看不到棋盘、点不到「推进」——**整个试炼通过 UI 都玩不了**，
而 20 项试炼断言全绿，因为它们都走调试 API 直接推进、绕过了界面。

修法：改成 `=== 'finished'`。并新增 `tools/ui_flow_test.py`：
**全程只用鼠标点击驱动**（调试 API 只用于读状态做断言），
覆盖试炼 / 无尽塔 / 工房三个交互链路。

### 5. 1Hz 刷新只更新了进度条，没更新按钮状态

工房产出攒够后，「领取」按钮**不会自动变为可用**——`renderProgressOnly` 当时只改了进度条
与"已积累"文本，待领取数字与按钮的 `disabled` 状态要等一次完整重绘才更新，
玩家不切页面就领不了。修法：把待领取数字与按钮状态一并纳入 1Hz 轻量刷新。

### 6. ⚠️ 最危险的一个：验收脚本本身在撒谎
`tools/run-tests.ps1` 最初只做一件事：在输出里 grep `FAIL:`。
问题是——**套件崩溃时根本打不出汇总行，自然也就没有 `FAIL:` 可匹配**，
于是脚本报"OK 零失败"，而实际上那个套件早就挂了。

真实后果：布局重构把 `.hud` 改成 `.topbar` 之后，`smoke_test` 的断言与
`page.evaluate(".hud-stat b")` 双双失效——前者失败、后者抛异常导致整个脚本崩溃。
但连续几轮我看到的都是"OK 零失败"，直到某次改用退出码统计才发现。

修法三条：
1. 判定改为 **退出码 + 文本双保险**（`exit != 0` 且无 FAIL 行 → 记为 `CRASH`）；
2. 运行器最后打印 `RESULT: ALL PASS/FAILED` 并 `exit 0/1`；
3. 修掉陈旧选择器（`.hud` → `.topbar`，金币改读 `[data-res="gold"]`），
   并修掉 relic 测试里"从 DOM 抓本章全部副本"的写法——它没考虑到副本列表
   现在默认只显示「待推进」，只抓到 1 个。

> 教训：**"测试全绿"这件事本身也需要被验证**。一个只会 grep 成功字样的脚本，
> 在套件崩溃时给出的是虚假的安全感。

### 7. 死代码：无尽塔其实没有层主

`isRestFloor(floor)` 最初写成 `floor % 5 === 0`，而 `makeFloorEnemies` 在休整层**直接返回空敌人**。
于是第 10 / 20 / 30 层永远是休整层，那句 `isBoss = floor % 10 === 0` 成了**死代码**——
整座塔没有任何 BOSS，是一条没有起伏的平坡。

修法：`isRestFloor` 排除层主层（5/15/25 休整，10/20/30 层主），并抽出 `isBossFloor`。

> 教训：**"每 N 层触发 X"这类规则互相重叠时，先触发的会静默吃掉后者。**
> 补上断言后才敢说层主真的存在。

### 8. 修完层主，塔变成了绝对硬墙

补上 BOSS 后，难度探针显示**5 局全部恰好停在第 9 层**——第 10 层层主需要约 266 秒才能打完，
而上限只有 150 秒；队伍也活不过 26 秒。既打不过、又毫无随机性
（战斗内核用期望值，墙是精确的）。

修法：`scalePerFloor` 28→24、超线性项 0.05→0.03、层主倍率 2.8→1.8、层主层敌人 3→2。
结果：15 级队伍到 **19 层**，55 级队伍到 **49 层**——墙能靠成长越过。

> 教训：加了难度尖峰之后，**必须重跑难度探针**；尖峰很容易从"挑战"变成"死路"。

### 9. ⚠️ 第二个"验收脚本在撒谎"：改完 src 跑测试，验的是旧包

`vite preview` 和 `singlefile_test` 都读**已构建的产物**。运行器原本只负责起
服务器、跑脚本、收退出码，于是出现这种情况：

```powershell
# 改完 src/styles.css
powershell -File tools/run-tests.ps1 -All
# → RESULT: ALL PASS     （全部跑在改动之前的 dist/ 上，改了等于没改）
```

同一类问题还有一个更隐蔽的版本：`balance_test` 从 DOM 抓副本列表
（`[data-action='pick-dungeon']`），而副本页默认筛选是**「待推进」**，
于是它只抓到 1 个副本、跑出 `1/1 通过` —— **全绿，但几乎没有覆盖**。

两处修法：

| 问题 | 修法 |
| --- | --- |
| 验旧包 | `run-tests.ps1` 加构建新鲜度闸门：`src/` 比 `dist/`、`dist-single/` 新就自动重建（`-NoBuild` 可跳过） |
| 静默缩水 | 测试自己带断言：过滤没生效（<5 个副本）直接 `return 1`；并断言**第 1 个副本必通**、模拟无空返回、无副本超过 300s |

> 教训：**测试"跑了"和测试"测到了"是两件事。** 任何从界面抓数据的测试，
> 都要先确认自己抓到的数量是对的，否则界面一改筛选默认值，测试就悄悄退化成空跑。

### 10. ⚠️ 测试卡死 = 没有结论：给每个套件加超时

真实发生过：整套跑完 10 个套件后，`balance_test` 卡在某次 Playwright 调用上，
**9 分钟零输出、零 CPU**，运行器就一直等下去——不失败、也不结束。
"卡住的套件"比"失败的套件"更糟：失败至少会给出结论，卡住什么都不给。

修法：每个套件用 `.NET Process` API 启动并 `WaitForExit(180s)`，超时就 `taskkill /T`
整棵树并记 **`TIMEOUT(180s)`**（退出码 124），整体判 FAILED。

顺手挖出两个 PowerShell 坑：

| 坑 | 现象 | 说明 |
| --- | --- | --- |
| `Start-Process -PassThru` + 重定向 | `$proc.ExitCode` **恒为 `$null`** | 即使 `WaitForExit()` 之后也是空 → 所有套件都被误判成 `CRASH(exit )`。改用 `System.Diagnostics.Process` 才有真退出码 |
| 遍历 chrome 进程做清理 | 差点杀掉用户自己的浏览器 | 只能按命令行里的 `playwright_chromiumdev` 临时 profile 精确清理，**绝不能 `Stop-Process -Name chrome`** |

另外 `smoke_test` 的多处 `.count()` 加了重试：刷新后立刻数元素偶尔会撞上渲染进程重建
（`Execution context was destroyed`），那是纯粹的时序抖动，不该报红。

### 11. ⚠️ git 把对象写坏了，但提交"显示成功"

发布脚本第一次跑就撞上了这个：

```
[main (root-commit) 4190d95] 更新源码（268 个文件）      ← 明明说提交成功
error: inflate: data stream error (incorrect data check)  ← 紧接着退出码 128
error: corrupt loose object '7528ca75fe07d9ea6025e8f13bdd3892290f9565'
```

`git fsck` 确认：一堆松散对象在**写入时**就坏了。这是**偶发**的，实测 4 次：

| 配置 | 干净 |
| --- | --- |
| 带 `-c core.fsync=all` | 2 / 2 |
| 不带 | 1 / 2 |

注意这张表的分量：样本很小，而且**后来又亲眼见到一次带 fsync 仍然写坏**。
所以"加个参数就修好了"是错的结论 —— 能依赖的只有"写完校验、坏了重建"：

| 环节 | 兜底做法 |
| --- | --- |
| 写对象 | `-c core.fsync=all`（降低概率）+ `-c core.autocrlf=false`（消掉一百多行 LF→CRLF 警告，不然真报错会被淹掉） |
| 打包 | `-c pack.threads=1` |
| 提交后 | `repo_is_sound()` 跑 `git fsck` **校验整个对象库**；不干净就删 `.git` 重新提交（源码都在工作区，`.git` 只是派生数据） |
| 推送时 | 失败自动重试最多 3 次，推完用 `git ls-remote` **核对远端提交号** |

这套兜底在同一次发布里就真的救了场：源码推送第 1 次因 `remote unpack failed:
index-pack abnormal exit` 失败，重试后成功并核对通过。

顺带两个同类坑：仓库属主与当前用户不一致时 git 会以 `detected dubious ownership`
拒绝一切操作（统一带 `-c safe.directory=*`，只对当次调用生效，不动用户全局配置）；
记事本/PowerShell 5.1 写出的 JSON 带 BOM，`json.loads` 会直接抛异常
（症状是"我明明填了仓库地址，脚本每次还问我一遍"）—— 读 JSON 一律用 `utf-8-sig`。

> 教训：**"命令返回成功"和"结果真的落盘了"是两件事。** 发布这种动作，最后必须有一次
> 独立核对（这里是 `ls-remote` 对提交号），否则你只是相信了一句 stdout。
> 另一条同样重要的：**验证一次修复，要拿数据说话。** 我第一次凭两次成功就写下
> "fsync 修好了"，第三次就被打脸了。

### 12. 浏览器测试的环境抖动：重试可以，但必须**打出来**

在真实浏览器里跑测试，偶尔会撞上这种报错：

```
Error: Page.evaluate: Execution context was destroyed, most likely because of a navigation.
```

它和被测代码无关，是渲染进程被换掉/重建（本机同时开着用户的 Chrome，测试又反复起停
headless Chrome，压力大时更容易出现），重跑同一个套件就过。观察到的三次抖动分别在
`balance_test`（卡死 9 分钟）、`smoke_test`、`tower_test`，每次都是不同套件。

处理方式收在 `tools/ui_harness.py` 里（`evaluate` / `count_of`），两条原则：

1. **只对明确的抖动特征重试**（`Execution context was destroyed` / `Target closed` /
   `Frame was detached`），其他异常照常抛出去；
2. **每次重试都打印一行**。静默重试会把真问题藏起来——那比直接失败更危险。

> 反过来也提醒一句：看到"重试成功"的日志时不要当成没事。同一个探针反复抖动，
> 说明环境有问题（内存、并发起的浏览器数），该治的是环境。

### 13. ⚠️ 往 `.ps1` 里写中文注释，把整个脚本写坏了

`run-tests.ps1` 开头就写着"ASCII-only on purpose"，我还是往里加了几行中文注释。
PowerShell 5.1 按 GBK 解 UTF-8 字节，某些多字节序列会解出 `"` 或 `\` 这类字符，
于是**脚本直接解析失败**：

```
Unexpected token '${status}' in expression or statement.
Missing closing '}' in statement or block.
```

看起来像语法错误，其实是编码问题——这类错误特别容易让人去改语法，越改越乱。
规矺：**`.ps1` / `.bat` 永远纯 ASCII**，中文输出一律交给 Python 打印（Python 源文件是 UTF-8）。
顺带一个同类坑：`"$status(retry)"` 在 PowerShell 里会被当成表达式，必须写 `"${status}(retry)"`。

### 14. 浏览器套件偶发卡死：超时 + 重试一次，但必须打印

`balance_test` 出现过两次"渲染进程卡住、`page.evaluate` 永远不返回"（0 CPU，两边都闲着）。
现在三层处理：套件内 `page.set_default_timeout(20000)` 让调用报错而不是干等；
运行器每套件 180s 超时；`TIMEOUT`/`CRASH` 自动**重试一次**并记 `PASS(retry)`、
在汇总里打印 NOTE。`FAIL`（断言真的没过）不重试——重试一次也不会变绿。

> 这条策略的边界要清楚：**允许偶发抖动，但不许它安静地发生。**
